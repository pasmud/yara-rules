# Synthetic YARA marker lab

Five curated [YARA](https://virustotal.github.io/yara/) rules demonstrate how to
turn synthetic file markers into reproducible detections. The Python runner
compiles the bundled catalog with the real YARA engine and scans one local file
at a time. All samples are inert text or generated bytes.

## Quickstart

From the checkout root, use Python 3.12 on Linux. Installation needs access to
the pinned wheel (from PyPI or a local wheelhouse); commands and tests run offline
after installation. No separate YARA executable is needed.

```sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install --only-binary=:all: -r requirements.txt
python -m yara_lab check
python -m yara_lab scan examples/intake-note.txt
```

Expected output from the last two commands:

```text
Catalog compiled.
Synthetic_Intake_Note
```

For a clean-file example, `python -m yara_lab scan LICENSE` prints nothing
and exits with status `1`. The CLI prints one rule identifier per line, sorted
by name, when multiple rules match.

| Exit | `check` | `scan FILE` |
| --- | --- | --- |
| `0` | Catalog compiled | At least one rule matched |
| `1` | — | No rule matched |
| `2` | Usage, dependency, or compiler error | Usage, dependency, compiler, input, or scan error |

Errors are written to stderr. A missing engine or a compiler warning fails the
command; an unsuccessful scan is never reported as a clean file.

For a machine-readable inventory, run `python -m yara_lab check --json`.
After successful compilation, stdout contains one JSON object with a `rules`
array sorted by `identifier`. Each entry has an `identifier`, a sorted `tags`
array, and a `meta` object preserving YARA metadata values. Object keys are
sorted and the output ends in a newline, so the same catalog produces the same
output. Compilation failures leave stdout empty and exit with status `2`.

## Rule catalog

| Rule | Match criteria | Likely false positives |
| --- | --- | --- |
| `Synthetic_Intake_Note` | The exact `LAB-INTAKE/1` header followed by LF or CRLF starts at byte zero, and the literal `status=training-only` appears somewhere in the file. | A template or exported note with that header and status marker. The status can be part of a longer string; this is not a key/value parser. |
| `Synthetic_Review_Trace` | The literal `LAB-REVIEW/1` and any two distinct literals from `queue=fixture-review`, `decision=manual-check`, and `owner=training-desk` appear anywhere. Repeating one field does not count twice. | Training logs, documentation, or concatenated notes that quote the marker and two fields, even from separate records. |
| `Synthetic_Archive_Tag` | Bytes start with ASCII `YLAB`, then version `0x01` and flags `0x00`. The literal `training-archive` starts at byte offset 8 through 31 inclusive (zero-based). | A generated file or format example that shares the prefix and early tag. This does not validate an archive structure. |
| `Synthetic_Practice_Receipt` | At byte zero, three consecutive lines read `LAB-RECEIPT/1`, `receipt_id=R` followed by exactly four ASCII digits, and `mode=practice`. Line breaks can be LF or CRLF; the mode line can also end at EOF. | A blank template with a sample ID or a copied receipt at the start of a file. Content after the opening record is not validated. |
| `Synthetic_Observer_Rollcall` | The `LAB-ROLLCALL/1` header followed by LF or CRLF starts at byte zero, and the literal `[seat:observer]` occurs exactly three times. | A sample agenda or quoted token can match. Adjacent tokens count separately, and the rule does not count distinct people or require one token per line. |

All literals are case-sensitive. A hit means the file contains the specified
fixture markers; it does not indicate maliciousness. No match means none of
these conditions held, not that the file is safe.

## Interface and limits

- `check` and `scan` use only [`rules/synthetic.yar`](rules/synthetic.yar).
  Rule includes are disabled; there is no rule discovery or custom rule input.
- `scan` accepts a local regular file (including a symlink to one) up to
  1 MiB (1,048,576 bytes), including empty files. It reads a bounded buffer
  once and passes those bytes to YARA with a two-second engine timeout. Use a
  stable file; reads are not atomic if another process changes the file.
- Python callers using `yara_lab.scanner.match_names(rules, data)` get the same
  byte limit and engine timeout. Oversized `bytes` raise `scanner.InputError`
  before the engine is called; no partial sample is scanned.
- This is a source-checkout CLI for controlled lab fixtures. It does not scan
  directories, stdin, processes, URLs, or archive contents, and it is not a sandbox.

## Offline rule review

1. Inspect the rule diff and run `python -m yara_lab check --json` to verify
   the compiled identifiers, tags, and descriptions.
2. Run `python -m unittest discover -s tests -p test_rule_review.py -v` to
   check the [synthetic review pairs](tests/test_rule_review.py) with real YARA.
   Each rule has a benign lookalike that is expected to match and a similar
   input that should not. For example, the intake rule matches a draft comment
   containing `status=training-only-draft` because it checks for a substring.
   Exact match lists also catch accidental hits from other rules.
3. For a rule change, decide whether each known benign collision should still
   match before updating expectations. Record any changed boundary or false
   positive in the rule catalog above. Add a pair for every new rule; the
   review test checks coverage against the compiled catalog. Run the full
   verification below before submitting the change.

## Verification

From the checkout root with the virtual environment activated:

```sh
python -m pip install --only-binary=:all: -r requirements-dev.txt
python -m ruff check .
python -m ruff format --check .
python -m yara_lab check
python -m unittest discover -s tests -v
```

The regression suite compiles the catalog and uses YARA to assert exact match
lists. It covers each rule, ordinary nonmatches, near misses, multiple hits,
binary offsets, the file size boundary, and CLI failures. GitHub Actions runs
the same checks on pushes and pull requests with read-only repository access.
